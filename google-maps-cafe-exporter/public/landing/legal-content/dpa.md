# Соглашение об обработке персональных данных / Data Processing Agreement

**Версия:** 1.0
**Дата вступления в силу:** [ДАТА]

Настоящее Соглашение об обработке персональных данных («**DPA**») является частью договора между:

**Клиентом**, определённым в соответствующем Заказе («**Контролёр**»),

и

**[ПОЛНОЕ НАИМЕНОВАНИЕ ИСПОЛНИТЕЛЯ]**, [АДРЕС, РЕГИСТРАЦИОННЫЙ НОМЕР] («**Обработчик**»).

DPA применяется в той мере, в которой Обработчик обрабатывает персональные данные от имени Контролёра.

## 1. Термины

Термины:

* personal data;
* processing;
* controller;
* processor;
* data subject;
* personal data breach;
* supervisory authority;
* special categories of personal data

имеют значения, установленные GDPR.

«**Customer Personal Data**» означает персональные данные, обрабатываемые Обработчиком от имени Контролёра при предоставлении сервиса.

## 2. Роли сторон

В отношении Customer Personal Data:

* Клиент является Controller;
* Исполнитель является Processor.

Каждая сторона самостоятельно исполняет применимые к ней обязанности GDPR.

Если Исполнитель самостоятельно определяет цели и существенные средства отдельной обработки, например собственную бухгалтерию, предотвращение мошенничества или управление своими договорными отношениями, для такой обработки он действует как отдельный Controller, и она регулируется Privacy Policy, а не настоящим DPA.

## 3. Предмет обработки

Обработчик может обрабатывать данные для:

* хостинга цифрового меню;
* работы административной панели;
* авторизации пользователей;
* технической аналитики;
* формирования отчётов;
* хранения настроек;
* оказания поддержки;
* резервного копирования;
* обеспечения безопасности;
* работы заказанных интеграций;
* исполнения документированных инструкций Контролёра.

Обработчик не вправе использовать Customer Personal Data для собственных независимых рекламных профилей или продажи персональных данных.

## 4. Продолжительность

Обработка осуществляется в течение срока действия договора и дополнительного технического периода хранения, установленного настоящим DPA или обязательным законодательством.

После завершения услуг применяются правила раздела «Удаление и возврат данных».

## 5. Документированные инструкции

Обработчик обрабатывает Customer Personal Data только:

* в соответствии с договором;
* настройками сервиса;
* действиями уполномоченных пользователей;
* иными документированными инструкциями Контролёра.

Если инструкция, по мнению Обработчика, нарушает GDPR или иное применимое законодательство ЕС о защите данных, Обработчик уведомляет Контролёра и вправе приостановить исполнение соответствующей инструкции до её уточнения.

## 6. Обязанности Контролёра

Контролёр отвечает за:

* наличие законного основания обработки;
* предоставление privacy notice субъектам данных;
* законность передаваемых данных;
* получение согласия, где оно требуется;
* корректную настройку cookies и analytics;
* обработку запросов субъектов данных;
* законность подключаемых интеграций;
* соблюдение национального законодательства.

Контролёр не должен без предварительного письменного согласования загружать в сервис специальные категории персональных данных, если такая обработка не предусмотрена конкретной функцией и отдельными гарантиями.

## 7. Конфиденциальность персонала

Обработчик обеспечивает, чтобы лица, имеющие доступ к Customer Personal Data:

* имели доступ только в необходимом объёме;
* были связаны обязательствами конфиденциальности;
* получили соответствующие инструкции;
* использовали данные только для выполнения своих обязанностей.

## 8. Безопасность

Обработчик обязуется поддерживать технические и организационные меры, соразмерные риску.

Минимальный набор мер после запуска production-сервиса описан в Приложении 2.

Обработчик вправе совершенствовать меры при условии, что общий уровень защиты не снижается существенно.

## 9. Управление доступом

Обработчик применяет принцип least privilege.

Доступ сотрудников и подрядчиков предоставляется:

* индивидуально;
* по роли;
* только на необходимый срок;
* с возможностью отзыва.

Для привилегированного административного доступа должна использоваться многофакторная аутентификация, где это технически возможно.

## 10. Sub-processors

Контролёр предоставляет Обработчику общее письменное разрешение на привлечение subprocessors.

Актуальный перечень публикуется:

**[URL SUBPROCESSOR LIST]**

До подключения нового subprocessor, который будет обрабатывать Customer Personal Data, Обработчик уведомляет Контролёра не менее чем за **15 дней**, если более короткий срок не необходим для устранения угрозы безопасности или соблюдения закона.

Контролёр вправе мотивированно возразить по причинам защиты персональных данных.

Обработчик обеспечивает договорные обязательства subprocessor, по существу эквивалентные обязательствам настоящего DPA в отношении соответствующей обработки.

Обработчик остаётся ответственным перед Контролёром за исполнение обязательств subprocessor в соответствии с GDPR.

## 11. Запросы субъектов данных

Обработчик, с учётом характера обработки, оказывает Контролёру разумную техническую помощь в исполнении запросов субъектов данных, включая:

* доступ;
* исправление;
* удаление;
* ограничение;
* переносимость;
* возражение.

Если субъект напрямую обращается к Обработчику по Customer Personal Data, Обработчик:

1. не отвечает по существу от имени Контролёра без разрешения;
2. перенаправляет запрос Контролёру;
3. оказывает разумную помощь.

## 12. DPIA и консультации

Обработчик предоставляет разумную информацию, необходимую Контролёру для:

* оценки воздействия на защиту данных;
* консультации с supervisory authority,

если такая обязанность возникает применительно к сервису.

## 13. Personal Data Breach

При подтверждённом или разумно предполагаемом нарушении Customer Personal Data Обработчик уведомляет Контролёра **без неоправданной задержки**.

Целевой операционный срок первичного уведомления — не позднее 24 часов после того, как соответствующая команда Обработчика получила достаточные основания считать, что произошло нарушение Customer Personal Data.

Уведомление, по мере доступности, включает:

* характер инцидента;
* категории данных;
* категории субъектов;
* вероятные последствия;
* принятые меры;
* контакт для взаимодействия.

Недостающая информация может предоставляться поэтапно.

Уведомление Обработчика не означает признания ответственности.

## 14. Security incident cooperation

Обработчик принимает разумные меры для:

* локализации инцидента;
* прекращения несанкционированного доступа;
* восстановления безопасности;
* сохранения необходимых журналов;
* содействия расследованию;
* предотвращения повторения.

Контролёр самостоятельно принимает решение о необходимости уведомления supervisory authority и субъектов данных, если закон не возлагает соответствующую обязанность непосредственно на Обработчика.

## 15. Аудит

Обработчик предоставляет информацию, разумно необходимую для подтверждения соблюдения Art. 28 GDPR.

Стороны в первую очередь используют:

* security documentation;
* результаты независимых проверок;
* сертификаты;
* penetration-test summaries;
* vendor compliance documentation,

если они доступны и достаточны.

Контролёр может провести дополнительный аудит не чаще одного раза в 12 месяцев, кроме случаев:

* существенного инцидента;
* требования supervisory authority;
* обоснованного подозрения существенного нарушения.

Аудит проводится:

* с разумным предварительным уведомлением;
* в рабочее время;
* без необоснованного вмешательства в работу;
* с соблюдением конфиденциальности других клиентов.

Расходы на индивидуальный аудит несёт Контролёр, если аудит не выявил существенного нарушения Обработчика.

## 16. Возврат и удаление

После прекращения услуг Контролёр может выбрать:

* удаление Customer Personal Data;
* возврат данных в доступном формате с последующим удалением.

Если Контролёр не дал отдельной инструкции, Обработчик удаляет активные Customer Personal Data в течение **30 дней** после окончания предусмотренного договором периода доступности.

Данные в резервных копиях могут сохраняться до окончания стандартного backup lifecycle, но не используются для обычной обработки и удаляются при штатной ротации.

Обязательное законное хранение допускается только в необходимом объёме.

## 17. International transfers — основной принцип

Обработчик не должен предоставлять Customer Personal Data получателю или персоналу в стране за пределами EEA, если для такой передачи не выполнены требования Chapter V GDPR.

До включения международной передачи стороны должны определить:

* участвующие страны;
* категории данных;
* получателей;
* применимый transfer mechanism;
* необходимые supplementary measures.

## 18. Передача в Беларусь и другие non-adequate jurisdictions

Если Customer Personal Data передаются либо становятся удалённо доступными из государства, не имеющего applicable EU adequacy decision, такая передача не должна начинаться до создания законного механизма.

В частности:

### 18.1. Когда импортёр не подпадает под GDPR для соответствующей обработки

При наличии необходимых условий стороны могут использовать действующие Standard Contractual Clauses Европейской комиссии и соответствующий Module.

### 18.2. Когда импортёр непосредственно подпадает под GDPR по Article 3(2)

Стороны не используют SCC 2021/914 в ситуации, для которой они юридически неприменимы.

До создания и документирования иного действительного Chapter V mechanism соответствующие персональные данные должны оставаться недоступными из третьей страны.

### 18.3. Дополнительные меры

При необходимости стороны проводят transfer assessment и применяют дополнительные:

* технические;
* организационные;
* договорные

гарантии.

## 19. Default EEA data architecture

Если конкретный Order Form не предусматривает иное, production-архитектура должна по возможности проектироваться так, чтобы персональные данные EU-посетителей и customer analytics обрабатывались внутри EEA либо иного допустимого региона.

Сырые identifiers не должны передаваться в третьи страны исключительно ради отображения агрегированной аналитики, если нужный результат можно получить после анонимизации или агрегации.

## 20. Государственные запросы

Обработчик, если это не запрещено законом:

* проверяет юридическую обязательность запроса;
* уведомляет Контролёра до раскрытия;
* раскрывает минимально необходимый объём данных;
* документирует запрос.

## 21. Records and cooperation

Обработчик ведёт необходимые записи своей processor activity в объёме, требуемом применимым GDPR.

Обработчик сотрудничает с компетентными supervisory authorities в пределах установленных законом обязанностей.

## 22. Приоритет

В случае противоречия:

1. обязательный transfer mechanism;
2. настоящий DPA;
3. Terms of Service;
4. Order Form,

если Order Form прямо не предоставляет более высокий уровень защиты персональных данных.

Коммерческие условия не могут уменьшать обязательные права субъектов данных.

# Приложение 1. Детали обработки

## A. Предмет

Предоставление SaaS-платформы цифрового ресторанного меню, CMS, hosting и analytics.

## B. Продолжительность

Срок действия договора плюс применимый период удаления и backup retention.

## C. Характер обработки

* collection;
* transmission;
* storage;
* organisation;
* retrieval;
* display;
* analytics;
* modification;
* deletion;
* backup.

## D. Цели

* предоставление цифрового меню;
* управление меню;
* предоставление tenant analytics;
* обеспечение безопасности;
* исполнение инструкций Клиента;
* support;
* backup.

## E. Категории субъектов

В зависимости от функций:

* посетители цифрового меню;
* сотрудники Клиента;
* администраторы аккаунта;
* представители Клиента;
* лица, использующие контактные/booking-функции, если такая функция включена.

## F. Категории данных

В зависимости от функций:

* IP/network metadata;
* browser/device metadata;
* session identifiers;
* language;
* referrer/source;
* interaction events;
* approximate location derived from network data, если используется;
* user account name;
* business email;
* role;
* audit log information;
* support communications;
* booking/contact information, если функция специально включена.

## G. Special categories

Не предполагаются по умолчанию.

Клиент не должен использовать сервис для special-category data без отдельного письменного согласования.

## H. Frequency

Continuous / recurring на период предоставления сервиса.

# Приложение 2. Technical and Organisational Measures

С даты production launch Обработчик поддерживает меры, соответствующие фактической архитектуре, включая:

### 1. Encryption

* TLS для передачи данных;
* encryption at rest на поддерживаемой инфраструктуре, где доступно;
* защищённое хранение secrets.

### 2. Access control

* уникальные учётные записи;
* role-based access;
* least privilege;
* MFA для привилегированных аккаунтов;
* своевременное отключение доступа.

### 3. Tenant isolation

Логическое разделение tenant data и обязательная server-side authorization для доступа к данным конкретного Клиента.

### 4. Logging

Журналирование существенных:

* admin actions;
* authentication events;
* publication actions;
* security events.

### 5. Application security

* dependency updates;
* security patching;
* input validation;
* protection against common web vulnerabilities;
* secure secret management.

### 6. Backups

* регулярные backups критичных данных;
* контролируемый retention;
* периодическая проверка возможности восстановления.

### 7. Incident response

Документированный процесс:

* detection;
* triage;
* containment;
* investigation;
* notification;
* recovery.

### 8. Data minimisation

Не собирать персональные данные, которые не нужны для предоставления заказанной функции.

### 9. Analytics minimisation

По умолчанию:

* не хранить raw IP дольше технически необходимого;
* не создавать cross-tenant advertising profile;
* использовать агрегированные данные там, где индивидуальный tracking не нужен.

### 10. Secure development

* code review для критичных изменений;
* staging/testing;
* dependency scanning;
* controlled deployment;
* rollback.

### 11. Vendor management

Проверять subprocessors с учётом:

* security;
* data location;
* contractual protection;
* transfer mechanisms.

### 12. Data lifecycle

Поддерживать документированный lifecycle:

`collect → active use → archive/backup → delete/anonymise`

# Приложение 3. Sub-processors

Актуальная production-версия таблицы должна быть опубликована по адресу:

**[SUBPROCESSOR URL]**

Для каждого subprocessor указываются:

* legal name;
* purpose;
* categories of data;
* processing location;
* transfer mechanism;
* privacy/security link.

До production launch таблица должна быть заполнена фактическими поставщиками инфраструктуры.
